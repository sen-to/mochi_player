# 0007 统一职责目录、模型边界与依赖方向

- **Status**: Accepted
- **Date**: 2026-10-27
- **Related**: [0003 持久化](0003-persistence-migration.md)、[编码指南](../guides/code-organization.md)

## 背景

按流程归拢代码后仍存在两套职责目录和不一致的边界：部分用例直接依赖具体数据库或网络实现，数据库又复用业务模型作为行类型。目录与类型后缀调整不足以解决表结构、展示字段和业务状态之间的耦合。

## 决策

1. 功能优先，流程保持就近维护；功能和流程内部统一使用 `ui / application / domain / data`，只创建有实际内容的目录。`app` 负责启动、路由、跨功能组装与生命周期；`core` 只承载跨功能能力；`l10n` 保留资源入口，手写状态与持久化也遵循同一分层。
2. `domain` 保存业务模型、输入语义、规则和共享能力契约；不依赖 Flutter 界面、数据访问 SDK 或具体适配。`application` 保存 Provider、用例、业务输入映射及调用方所需的仓库 / 后端契约，不导入 `data`。
3. `data` 实现能力契约并持有具体 SDK、SQL 和外部响应转换；`ui` 通过应用入口工作。具体实现只由应用组装入口选择。数据库实现直接使用 `AppDatabase`，共享连接与公共读写不另设 Store 包装层。共享图片组件是界面资源适配边界，功能 UI 不直接依赖缓存实现。
4. 数据库独立生成 `MovieDO / TVShowDO / SeasonDO / EpisodeDO / MediaFileDO / StorageSourceDO`。记录只保存持久化字段；业务模型不再通过 `UseRowClass` 或 SQL `WITH` 充当数据库行。
5. DO 与业务模型通过数据层 Mapper 转换，原始 JSON 与服务结果通过外部服务 Mapper 转换，业务模型与 VO 通过展示 Mapper 转换。VO 只保存展示字段，不包办转换；可独立使用的业务输入模型与 Mapper 分开。
6. Provider 管理状态与已接受操作；连接、引擎、订阅、浮层及任务继续遵守明确的资源所有权。统一分层不改变原有扫描完整性、进度局部更新和关闭顺序。
7. 手写文件的职责、边界和解释性注释使用中文；生成代码使用生成工具维护。架构检查进入 CI，阻止旧目录、反向依赖、数据库模型复用和缺失说明重新出现。

## 数据兼容性

仅更换 Dart 行类型和边界转换，不修改六表的物理结构。保留 schema 2；用此前导出的 schema 2 创建旧库，再以新数据库实现重开，验证结构、JSON、枚举、凭据和观看状态。已有版本 1 开发库策略不在本次变更中扩大。

Drift 支持通过数据类命名生成独立行类型；SQL 表使用 `AS` 指定生成记录名称，而 `WITH` 用于既有 Dart 类型。依据：[表定义](https://drift.simonbinder.eu/dart_api/tables/)、[SQL 表与生成类型](https://drift.simonbinder.eu/sql_api/drift_files/)（核对日期 2026-10-27）。

## 取舍与重估条件

显式 Mapper 增加边界转换代码，但表字段、网络响应、展示格式可以独立变化。映射不发起查询，批量读取后在内存中转换，不增加逐条 SQL。结果、进度或后端流等同一接口的伴随类型可以就近放置；不为凑齐术语复制一套无差异 DTO。

未来新增持久化或远程协议时，沿同一边界增加记录 / DTO 和 Mapper，不在业务模型内加入序列化或 SDK 依赖。只有实际领域约束或独立部署需求变化时才重新讨论更深的架构层次。
