# 0001 多窗口策略：保留独立播放器，主窗口关闭即退出应用

- **Status**: Accepted（决策已接受，实施进度见下文）
- **Date**: 2026-10-11（初稿 2026-10-05）
- **Related**: [0002 播放引擎](0002-playback-engine.md)、[0003 持久化迁移](0003-persistence-migration.md)、[0005 SMB 播放路径](0005-smb-playback-path.md)

## Context（背景与约束）

产品需求：

- 播放器保留独立窗口，支持 mini、置顶和全屏；同一时间只保留一个播放器窗口。
- **关闭媒体库主窗口即退出整个应用，播放器窗口必须一并关闭，不允许留下后台播放或应用进程。** 最小化不属于关闭。
- 单独关闭播放器窗口只结束播放，媒体库主窗口继续运行。

2026-10-11 用户确认第二条，取代初稿中「关闭主窗口后播放器继续播放，直到最后一个窗口关闭才退出」的要求。窗口关闭必须先完成有界的退出清理，不能直接销毁主引擎后再尝试保存播放进度。

当前使用 `desktop_multi_window` 0.3.1，一个窗口一个 Flutter 引擎。主要边界与代价如下：

1. Windows 曾出现打开播放器后主窗口鼠标、键盘无响应的现象。当前 [runner](../../windows/runner/flutter_window.cpp) 使用 `UIThreadPolicy::RunOnSeparateThread`，处理 UI 与 Win32 消息线程共用时同步窗口调用阻塞的问题。多引擎、插件调用与线程策略需要结合复现和诊断验证，不能直接断言「多引擎是根因」或「更换插件必然修复」。
2. 主窗口与播放器分别初始化后台 drift + SQLite 连接，使用 WAL、`busy_timeout` 和字段级更新协调访问。多连接是当前支持的实现；跨独立连接的 drift 查询订阅不会自动共享失效通知，播放器目前在关闭或切换时回传变更键，由主窗口显式刷新。
3. 本轮实施前，窗口启动串行化、就绪等待、旧窗口退役与业务播放流程集中在 `player_window_app.dart`。本轮已抽取窗口服务和播放器窗口协调器，实施状态见下文。

Flutter 官方 Desktop Windowing API 提供单引擎多视图方向。[官方公告](https://flutter.dev/blog/desktop-windowing-apis) 将其列为 main 通道的实验能力。2026-10-12～13 的独立原型已验证 macOS 基础窗口、media_kit 纹理、输入、生命周期和 Release 基础运行，详见 [实验记录与证据](../experiments/official-single-engine-windowing.md)。当前不直接切换生产实现，基础验证成功不等于完整业务与双平台迁移通过。

### SDK 与小窗的重构依据（2026-10-13 补充）

- **底层能力与 Dart 窗口 API 分开判断**：stable SDK 已包含多视图底层接口；项目 3.47.2 的 macOS `FlutterViewController` 可连接现有引擎。但官方 `WindowController` 等实验 API 的正常启用仍受通道限制，不据此声称 stable 完全不支持单引擎多窗口，也不声称 stable 下的新 API 已验收。
- **通道限制有源码依据**：项目 3.47.2 的 `features.dart` 中 `windowingFeature` 只设置开发侧 `master.available=true`，stable / beta 默认为 false；`flutter_features.dart` 的 `isEnabled` 在通道不可用时先返回 false，然后才读取开关。main 与固定提交快照按该 SDK 的通道映射处理；不是在 stable 的启动命令上追加普通参数就能获得这套 API。
- **FVM 可管理实验 SDK**：下载方式不改变功能开放状态。后续采用 main API 时，在 `.fvmrc` 用已验证提交号固定 SDK，例如本次 `b314ad53146b1bde55b60197a35183fb530aac0a`，避免仅写 `main` 导致更新后 API 漂移。团队与 CI 均按固定版本复现。无需自行编译 Flutter 引擎，正常 SDK 工具下载对应预编译产物。
- **实验开关不限制 Release**：原型使用自己的 `flutter.config.enable-windowing=true`，Debug 与 macOS Release 均成功；Release `.app` 可直接运行，使用者无需 Flutter SDK。正式项目的 SDK 升级、全部依赖、Windows Release、签名 / 公证仍需另行验收，不把「实验」解释为「无法打包发布」。
- **macOS 小窗优先评估系统 PiP**：用户希望采用系统画中画，而非仅把 Flutter 播放器窗口缩小后置顶。AVKit 管理画中画窗口；该能力独立于 Flutter 官方多窗口 API，stable 应用也可通过原生桥接接入。当前 media_kit/libmpv 输出 Flutter 纹理，必须验证视频内容接入、字幕、播放控制、回到原播放器及退出清理，不能仅调用 PiP 开关就认定接入完成。系统 PiP 方案尚未实现或验收，不在本轮修改 mini 行为。
- **置顶不是引擎能力的否决条件**：如保留普通 mini 窗口，可通过系统窗口接口扩展；如采用系统 PiP，则按 PiP 的产品行为验收。两者分别评估，不因 Flutter 没有通用 always-on-top 方法就否定官方单引擎方案，也不将 macOS PiP 自动推广为 Windows 方案。

## Decision（决策）

**独立播放器窗口是产品目标；引擎数量与窗口插件是可替换的实现细节。主窗口是应用生命周期的入口，关闭主窗口必须协调关闭播放器并退出进程。**

### 窗口边界

1. 抽取统一的 `WindowService` 与 `WindowHandle`，承接创建、激活、关闭、尺寸、置顶、全屏和关闭事件；插件专属 API 集中在后端适配层，就绪等待、超时与退役逻辑由播放器窗口协调器管理。
2. 业务层只依赖窗口服务，不直接调用 `desktop_multi_window`。应用退出由独立的退出协调器管理，不把进度保存、数据库关闭等业务清理塞入通用窗口接口。
3. 跨窗口播放契约携带 `sourceId + path`；未入库的临时文件可以附带文件名、大小等最小回退元数据。不传已解析 URL、请求头、凭据或活动中的 provider 实例。接收方负责解析播放目标。
4. 播放器 UI 与窗口模式不依赖引擎数量；适配层负责每个窗口的插件注册、视图绑定和原生事件路由。窗口接口统一并不代表视频渲染与插件兼容已经解决。

### 数据库写入策略

保留现有两个后台 SQLite 连接，不把「主窗口唯一写入」作为本 ADR 的强制任务。SQLite WAL 支持多个连接并协调写事务，同一时刻一个写事务不等于应用只能由一个窗口提交写入，见 [SQLite WAL 并发说明](https://www.sqlite.org/wal.html)。

- 扫描、匹配、进度、收藏继续按各自字段更新，相关批量操作保持事务性。
- 跨连接的界面刷新必须显式通知；实时进度同步如有产品需求，单独补充通知协议。
- 如果出现实测锁竞争、写入超时，或统一状态通知的收益足够明确，再评估单写者；不能仅因多窗口就引入额外写入 RPC。
- 若以后采用主窗口承载写入服务，必须保持主引擎及服务存活至播放器最后进度提交并确认完成。协议需定义会话标识、顺序、提交确认、超时及失败处理；「消息已发送」不能视为「已落库」。

### 关闭主窗口与应用退出

主窗口原生关闭按钮、应用退出命令及平台可拦截的退出请求统一进入退出协调器，执行以下顺序：

1. 进入退出状态，拦截主窗口的立即销毁；拒绝新的播放器创建、替换请求和扫描 / 刮削任务，并协调正在启动或退役的窗口，避免退出期间出现新窗口。
2. 请求播放器停止播放，抓取最终进度，等待已排队写入及强制保存完成，再释放播放资源。当前多连接方案由播放器自己提交；未来单写者方案由主窗口写入并返回提交确认。
3. 播放器完成清理后返回确认并关闭；确认需要代表保存与清理结果，不能仅靠调用发送成功或窗口消失来推断落库成功。
4. 主窗口取消或等待后台任务收尾，等待必要的数据库写入、设置保存和连接关闭，最后销毁主窗口并结束整个进程。保持通信和数据库服务可用至相关清理完成。

退出请求必须幂等，重复点击不能重复清理或启动新的退出流程。请求、等待确认和整体清理均须有超时；超时时记录失败阶段，在尽力保存后关闭残留窗口并退出，不能无限挂起或继续后台播放。当前实现：常规窗口 RPC 默认 3 秒、启动最多 10 秒；播放器准备关闭的五个阶段各最多 2 秒，主窗口等待准备结果最多 12 秒、等待窗口消失最多 3 秒。应用退出的播放器阶段最多 18 秒，主窗口清理最多 8 秒，最后结束整个进程；macOS 原生退出命令另有 30 秒兜底。

单独关闭播放器复用其保存与资源释放流程，但不触发应用退出。正常退出应保证最后进度落库；进程被强制终止、系统断电或清理超时情况下，只能保证此前成功提交的数据，不承诺最后快照完整。

## 实施状态与跟进

2026-10-11 已实施：

- drift + SQLite、WAL 与 busy timeout、字段级写入、SQL 查询与分页订阅，保留两个窗口的独立后台连接。
- [WindowService / WindowHandle](../../lib/core/platform/window_service.dart) 与 [DesktopWindowService](../../lib/core/platform/desktop_window_service.dart) 隔离插件 API；启动、复用和退役由 [PlayerWindowCoordinator](../../lib/features/playback/application/player_window_coordinator.dart) 串行协调。
- [ApplicationExitCoordinator](../../lib/app/application/application_exit_coordinator.dart) 与 [MainWindowLifecycle](../../lib/app/application/main_window_lifecycle.dart) 接收主窗口关闭 / 平台退出请求；macOS 菜单、快捷键及 Dock 退出通过原生通道进入同一流程。
- 两阶段关闭协议：`player.prepareClose` 等待会话收尾、最终进度、资源释放、视图解绑与子数据库关闭，返回保存 / 释放结果和失败阶段；确认后发送 `player.close` 并等待窗口消失。`player.closed` 只用于变更通知，不用来推断保存成功。
- 退出请求幂等、分阶段超时；退出开始后禁用窗口交互并拒绝新播放请求，扫描停止后续发现 / 失效清理，刮削不再派发新任务，等待已接受的设置写入。启动中或失联的子引擎最终随整个进程结束。
- 自动化回归覆盖启动与退出竞争、重复退出、失败 / 无响应、最终保存顺序、切集期间退出和设置队列收尾；真实文件 SQLite 测试验证最终快照关闭重开后仍存在。
- macOS 原生双窗口检查通过：单独关闭子窗口后可再次创建；存在子窗口时关闭主窗口，以及子窗口聚焦时 Cmd+Q，均按子窗口保存 / 清理、主数据库关闭、进程退出顺序完成。检查使用隔离 SQLite 与模拟播放资源，不替代真实视频验收。

待验收 / 跟进：

- Windows 原生关闭、mini / 全屏、子窗口无响应与进程退出的运行时验证；本轮开发环境为 macOS，不把跨平台单元测试或 macOS 构建视为 Windows 验收。
- 两平台真实视频播放下的 mini / 全屏退出、连续创建 / 替换 / 关闭与播放资源回收压力测试。
- Windows 冻结场景的复现、线程与调用链诊断；通过验证后再更新已知限制。
- 官方单引擎多视图仅按下方门槛制作原型，当前继续使用现有窗口后端，不强制改为数据库单写者。

## 官方窗口方案的迁移门槛

先制作独立原型，验证后再决定迁移。须在项目目标 Flutter 版本的 macOS 与 Windows 上同时满足：

1. 主窗口与次级独立窗口的创建、聚焦、尺寸、mini、置顶、全屏及关闭事件符合产品要求。
2. `media_kit` 视频渲染、插件注册与视图绑定正常；音视频播放、seek、字幕、切集和资源释放通过验证。
3. 主窗口关闭能完成最终进度保存、关闭全部窗口并结束进程；播放器单独关闭、重复退出、启动中退出和无响应超时均通过验证。
4. 数据查询刷新与播放状态同步正确，连续打开 / 替换 / 关闭播放器不会导致输入冻结、残留窗口或资源泄漏。
5. 能在项目锁定 SDK 下构建和发布，两平台回归检查具备可复现记录；API 稳定性满足维护要求。

基础可行性原型已归档并从活动实验目录移除，SDK 提交、验证结论、来源与后续方法保留在 [实验记录](../experiments/official-single-engine-windowing.md) 中；实验机器日志与源码压缩包不提交到仓库。剩余验证按该文档的清单推进：Windows Debug / Release、系统 PiP、实际播放与项目插件、SQLite 最终保存、退出竞争 / 无响应，以及持续运行和多显示器。生产迁移前仍须满足上面的门槛；归档不表示所有门槛已通过。

不预先规定「先播放器、后主窗口」。若新旧窗口后端可以共存且生命周期、插件注册均验证通过，可以分步替换；否则统一迁移窗口宿主。迁移期间只保留有明确期限的适配实现，验收通过后删除旧后端，不长期维护两套业务流程。

## Consequences（后果）

- **正面**：保留独立播放器价值；应用退出语义明确；窗口后端更换集中在适配边界；避免为未经证实的数据库问题过早增加写入 RPC。
- **代价**：退出必须跨窗口协调，增加有界等待、失败处理与竞争测试；窗口抽象不能消除平台故障，也不能保证更换实现后业务层完全无需调整。
- **用户影响**：关闭主窗口会结束播放；希望继续观看时应最小化主窗口。旧的关闭后继续播放行为不再是产品目标。

## Alternatives（备选）

| 备选 | 当前评价 | 重新考虑条件 |
| --- | --- | --- |
| 应用内播放页面，取消独立窗口 | 实现较简单，但失去独立 mini 与置顶观看的价值 | 产品明确放弃独立播放器需求 |
| 原生窗口与原生播放器渲染 | 需要分别处理 macOS / Windows 的窗口、渲染、输入与生命周期，维护成本高 | 现有后端存在已验证的阻塞缺陷，官方方案也无法满足验收要求 |
| 继续使用 `desktop_multi_window`，通过窗口服务隔离 | 当前方案；保留已验证可用的实现，同时降低后续替换成本 | 依赖与目标 SDK 不兼容，或无法修复影响主流程的平台问题 |
| 立即采用官方实验 API | 适合原型验证，当前不直接作为生产替换 | 达到上面的双平台迁移门槛 |
| 主窗口承载数据库单写者 | 新生命周期规则允许该方案，但仍需写入确认和退出协调，并增加通信复杂度 | 实测并发问题或统一状态管理需求证明其收益 |

## Revisit trigger（重估触发条件）

1. 官方 API 的通道、稳定性或插件支持发生变化，足以启动迁移原型验证。
2. Windows 冻结可稳定复现、影响扩大，或定位到需要替换窗口后端的问题。
3. `desktop_multi_window` 与项目目标 Flutter 版本不兼容，或关键缺陷长期无法修复。
4. 多连接出现实测写入错误 / 超时，或需要播放过程中的实时状态同步。
5. 产品重新要求主窗口关闭后继续播放；届时必须重新设计应用宿主与写入服务的生命周期，不能直接恢复旧退出行为。
