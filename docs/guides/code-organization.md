# 代码组织与新增功能

本文规定后续新增和修改代码的目录骨架与职责边界。当前实现、命名约定及资源所有权见 [架构总览](../architecture/overview.md)；运行与检查命令见 [测试指南](testing.md)。这里的规则指导增量开发，不代表现有代码已满足严格 Clean Architecture，也不要求为统一目录而重写已有实现。

## 目录骨架

项目按功能组织，功能内部按职责分层。下图是新增代码的落位模板；只创建有实际内容的目录，不要求每个功能凑齐四层。

```text
lib/
├── main.dart                     # 初始化与启动入口
├── app/
│   ├── bootstrap/                # 选择实现、构造与注入依赖、窗口工厂
│   ├── application/              # 应用级生命周期与退出协调
│   ├── routing/                  # 路由与导航路径
│   └── presentation/             # 应用外壳、导航与布局
├── features/
│   └── <feature>/                # 当前为 home、library、playback、settings
│       ├── domain/               # 功能模型、业务规则与领域契约
│       ├── application/          # 状态 Provider、用例 Service、会话协调与所需契约
│       ├── infrastructure/       # 持久化、外部服务与播放后端的具体实现
│       └── presentation/         # 页面、组件、界面交互控制
│           ├── pages/
│           ├── widgets/
│           └── controllers/      # 有需要时创建
├── core/
│   ├── domain/                   # 多个功能共同使用的模型、规则与契约
│   ├── infrastructure/           # 共享数据库、存储协议与 TMDB 实现
│   ├── platform/                 # 视图窗口接口与平台桥
│   ├── ui/                       # 共享主题、组件与展示格式
│   └── formatters/               # 当前共享媒体格式工具
└── l10n/                         # ARB、语言 Provider 与生成的本地化代码
test/                             # 按被测代码的路径组织单元与 Widget 测试
integration_test/                 # 需要真实应用、原生插件或窗口的集成测试
tool/                             # 开发与验证脚本，不放应用运行时业务
macos/、windows/                   # 原生宿主与平台桥实现
```

不要在 `lib/` 顶层另建一套全局 `providers / services / repositories / pages`，与 `features/` 并行组织同一业务。文件在功能内按职责归属，类型后缀按 [统一命名约定](../architecture/overview.md#命名约定)选择；Provider、Controller 和 Service 不各自代表固定的一层。

## 决定代码归属

先判断“属于哪个功能”，再判断“承担什么职责”：

| 新增内容 | 放置位置与边界 |
| --- | --- |
| 单个功能的页面、对话框、组件 | `features/<feature>/presentation/`；只处理输入、展示及界面交互 |
| 面向界面的共享状态与操作入口 | 所属功能 `application/` 的 Provider；组件内部短暂状态可以留在组件中 |
| 扫描、刮削、连接测试等业务编排 | 所属功能 `application/` 的 Service；管理任务顺序、取消、错误和清理 |
| 播放队列、续播规则等功能模型与规则 | 所属功能 `domain/`；跨功能确实共享时才放 `core/domain/` |
| 功能专属数据库查询或后端适配 | 所属功能 `infrastructure/`；通过应用入口供页面使用 |
| 应用用例需要的持久化 / 后端契约 | 放在调用方所属的 `application/`，如 `PlaybackMediaRepository`、`PlaybackEngine`；领域本身需要的契约放 `domain/` |
| 跨功能共享的协议连接、数据库或外部能力 | `core/infrastructure/`；业务任务编排仍留在所属功能 |
| 通用窗口操作与原生能力适配 | Dart 接口与适配放 `core/platform/`，原生实现放对应平台 runner；播放器模式控制仍属 `playback` |
| 跨功能 UI、主题与格式化 | `core/ui/`；已有媒体格式工具继续复用 `core/formatters/` |
| 依赖实现选择与跨功能装配 | `app/bootstrap/`；业务对象通过构造参数接收依赖 |

“可能以后复用”不构成移入 `core` 的理由。功能专属对象即使被启动入口创建，也仍属于该功能；共享代码须具有明确的跨功能用途。`core` 不导入 `features` 或 `app`。

避免新建职责含糊的 `CommonService`、`Manager` 或大杂烩 `utils`。优先使用表达实际能力的名称；小工具归入其功能或能力目录，复用已有实现。

## 依赖与组装规则

1. 页面通过 Provider、应用 Service 或交互 Controller 发起业务操作，不直接查询 SQLite、持有具体数据库仓库、读取媒体源凭据或创建协议连接。展示资源加载与视图级窗口操作的既有边界见架构总览。
2. 应用层负责用例与状态，调用仓库和外部能力；不要让仓库负责弹窗、导航或页面状态，也不要让 Provider 承担 SQL、协议细节和播放器后端属性适配。
3. 基础设施实现可以使用领域模型及应用契约，不能反向依赖页面、Widget 或界面 Provider。新增业务规则尽量保持独立于 Widget、数据库查询和外部 SDK；现有 drift 行模型复用不要求顺带拆出重复模型。
4. 保持单向跨功能协作，不导入另一个功能的页面或具体基础设施，也不形成循环依赖。已有功能之间的应用入口调用可以延续；新协作优先通过显式契约、回调或在 `app/bootstrap` 组装共享能力，不为绕过循环把业务整体搬进 `core`。
5. 数据库、设置、TMDB 等共享依赖在启动入口创建并注入；视图资源按视图创建，播放资源按会话创建。不增加静态全局实例、隐藏服务查找或构造参数缺失时自动创建依赖的兜底路径。
6. 接口用于明确调用边界、替换后端或隔离测试依赖，按调用方所需能力设计。已有具体仓库调用可以保留；不为每个类机械增加接口、转发 Service 或一表一仓库。

新增订阅、连接、计时器或后台任务时，要同时确定所有者和关闭顺序。主视图与播放器共享应用状态；不要新增语言 / 设置快照、窗口 RPC 或独立数据库连接来同步同一引擎内的状态。退出与窗口行为遵循 [播放生命周期](../architecture/playback.md#生命周期与退出) 和 [ADR 0001](../decisions/0001-multi-window-strategy.md)。

## 新增功能示例

以“媒体库手动修正匹配”为例，以下是落位示例，不表示功能已经实现：

| 内容 | 建议归属 |
| --- | --- |
| 搜索与确认匹配的对话框 | `features/library/presentation/` |
| 展示候选项、加载状态与用户操作入口 | 复用媒体库 Provider，或在状态确需独立时新增功能 Provider |
| 查询候选、应用选择、协调保存 | `features/library/application/` 的用例 Service |
| 匹配选择及校验规则 | `features/library/domain/` |
| TMDB 请求 | 复用注入的共享 TMDB 能力 |
| 元数据和媒体关联写入 | 复用既有持久化边界；新增查询 / 写入放对应仓库或数据库实现 |
| 构造与注入新增对象 | `app/bootstrap/application_dependencies.dart` |

不要从对话框直接调用数据库或 TMDB 后再追加一个仅转发方法的 Service。优先沿已有调用链扩展，确有独立状态、业务步骤或替换需求时再拆分对象。

## 编码与评审流程

### 表单布局约定

- 输入字段可以使用固定标签列；开关、操作按钮等设置行使用内容宽度的控件，文字区域占据剩余空间。开关行复用 `SettingsSwitchItem`，不要重复固定宽度的标签与开关布局。
- 辅助说明默认允许换行，表单行采用最小高度并随内容增长，不用单行省略隐藏操作后果、错误原因或必要路径。需要更大文字区域时，使用 `AppFormItem.subtitleBelowControl` 将说明放到整行下方。
- 占位提示说明输入格式或提供简短示例，不重复字段标签，也不把示例当作实际默认值。WebDAV 主机提示 IP / 域名，端口提示“如：5244”，新增 WebDAV 路径输入留空并显示 `/dav` 占位示例（留空提交仍表示根路径 `/`）；端口必填，测试与保存均校验 1–65535 范围内的整数，不依赖留空推断。编辑已有地址时显示该 URL 的实际端口（包含 HTTP / HTTPS 的 80 / 443）。5244 是 OpenList 等服务的示例端口，不是所有 WebDAV 服务的默认值。
- 状态与操作保持统一：媒体源连接测试保留标题，结果用标题下方的小字显示，成功仅显示“连接成功”，失败显示可换行的原因；右侧按钮按内容宽度居中对齐。兼顾中英文与系统字号放大，修改共享布局时检查窄弹窗。

上述约定参考 [Ant Design Form](https://ant.design/components/form/) 的标签 / 辅助说明分工与 [MUI Switch](https://mui.com/material-ui/react-switch/) 的开关 / 标签组合能力，具体布局由本项目的桌面表单组件实现。

### 开发检查

- 开始编码前阅读架构总览、本指南及相关功能文档 / ADR，找到已有调用入口与可复用能力。
- 确定目录归属、类型职责、依赖来源与资源所有者后再实现；遵守现有命名，不因新增功能整体改名。
- 修复或替换实现时移除废弃路径，不增加旧名别名、重复入口或无调用方的兼容转发。确有兼容需求时，在文档中明确对象、理由与移除条件。
- 测试围绕业务行为和边界组织，按 [测试指南](testing.md) 选择单元、Widget 或原生集成验证；不为低影响的目录调整添加只复述实现的测试。
- 完成后检查是否出现页面访问基础设施、模块循环、隐藏依赖创建、重复实现或资源未释放；执行受影响的检查，并同步架构文档。技术方向变化更新 ADR，交付阶段变化更新 `status.md`。

本骨架的变更应有明确的职责或依赖问题作为依据。外部 Flutter 项目的目录可用于研究取舍，不作为改变本项目规则的直接理由。
